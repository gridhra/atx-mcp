# ROADMAP — 「Adobe 製品に可能なことは理論上再現できる状態」へ

作成日: 2026-08-21 / 前提: 非生成的(決定論的)操作のみを対象とする。
生成系(Generative Fill、超解像等)は恒久的に対象外 — 外部モデルの前後処理として本ツールが挟まる、という現在の役割分担を維持する。

## 完備性の定義(ゴール判定)

「Adobe の任意の非生成的操作履歴 H に対して、次の3条件を満たすこと」:

1. **op 存在**: H の各ステップに対応するオペレータがレシピ DSL に存在する
2. **合成可能**: レイヤースタック + マスク + ブレンドモードで H の構造を表現できる
3. **決定論**: レシピとして保存・再実行でき、バイト同一の出力を返す

(2) を満たした時点で、未実装フィルタは「まだ書いていない op」にすぎず、アーキテクチャ上のゴールは達成とみなす。

## 資産の分解

| # | 資産 | Adobe での実体 | atx の現状 |
|---|---|---|---|
| 1 | 画素エンジン | 16bit/f32 リニアライト、カラーマネージド | RGBA8、sRGB 前提 |
| 2 | 合成モデル | レイヤー + ブレンドモード + 不透明度 | なし(直列パイプライン) |
| 3 | マスクモデル | 選択範囲、グラデ/放射/輝度マスク、部分適用 | なし |
| 4 | オペレータ群 | カーブ、HSL、シャープ、遠近、レンズ補正… | 基本7 op |
| 5 | 入出力 | RAW、ICC 完全対応、LUT、PSD | JPEG/PNG/WebP/AVIF、ICC は温存のみ |

本丸は 1〜3。4 は個別実装の積み上げ、5 は翼。

## フェーズ計画

### Phase A — 調整系の完成(現行アーキテクチャのまま、破壊なし)
- `curves`(チャンネル別トーンカーブ、制御点列)/ `levels`
- `white_balance`(色温度/ティント)
- `hsl`(色相域別 Hue/Sat/Lum シフト = Lightroom HSL パネル)
- `lut`(.cube 3D LUT 適用)
- `perspective`(台形/キーストーン補正。フィールド FB P4)
- ぼかし族: gaussian / median / bilateral、ノイズ除去(初版は wavelet or NLM)
- 到達点: Lightroom の「全体調整パネル」相当。実務需要の大半をカバー

### Phase B — 画素エンジン v2(最重要・唯一の破壊的変更)
- 内部表現を f32 リニアライトへ移行。入口で ICC → 作業色空間、出口で逆変換(lcms2 を feature flag で導入)
- `ENGINE_VERSION` を 2 に上げ、ゴールデンテストを世代管理(v1 ゴールデンは凍結保存)
- 8/16bit 入出力、既存 op を f32 パスへ移植(決定論維持: 固定丸め規則を明文化)
- **Phase C より先に実施する**こと。合成モデルを 8bit 上に作ると全面作り直しになる

### Phase C — マスクと局所適用(Lightroom の完成)
- マスク = グレースケール revision として第一級アセット化(ストア変更は不要、mime で区別)
- 任意の調整 op に `mask: <revision_id>` 参照を付与可能に
- 決定論的マスク生成 op: linear_gradient / radial_gradient / luminosity_range / color_range
- 検出系マスク(被写体・空・顔)は「検出ツールが候補マスクを revision として返し、採否・合成はホスト AI が指示」— 既存の detect_tilt と同じ設計思想。ML 推論を入れる場合も ONNX 固定重み + 固定前処理で決定論を保つ
- MCP: `render_preview` にマスクの可視化 overlay を追加

### Phase D — レイヤーグラフ(Photoshop の完成)
- レシピ DSL v2: 直列 `operations` → `layers: [{source, ops, mask, blend_mode, opacity}]` のスタック
- v1 レシピは「1レイヤーのスタック」として無損失に埋め込める → 後方互換・ハッシュは v2 で別世代
- ブレンドモード: separable 系(multiply, screen, overlay 等)から実装、W3C compositing 仕様を参照実装として検証
- クローン / ヒーリング(PatchMatch 系。シード固定で決定論的に実装可能)
- `compare_revisions` の差分モード(diff 画像)もここで自然に入る

### Phase E — 入出力の翼
- RAW 現像: `rawler`(純 Rust)でデモザイク → Phase B の f32 パイプラインに直結
- レンズ補正: lensfun DB(歪曲・周辺減光・倍率色収差)
- PSD: 読み(`psd` crate)のみ対象、書きは非目標と明示
- SVG ラスタライズ(`resvg`): テキスト・図形・ロゴの焼き込み(Illustrator 領域への最小限の橋)
- LUT 書き出し(レシピの調整部分を .cube 化 = 他ツールへの持ち出し)

## フィルタ資産戦略(量で Adobe を追う方法)

Adobe の強さの一半は既存アセット(フィルタ・プリセット・LUT・アクション)の量的質にある。
これをコード実装の積み上げで追うのではなく、**「メタ op 少数 × データ資産無限」**の構造で追う:

1. **メタ op**(Phase A に組込): `color_matrix`(4×5 行列 = セピア/色相回転/チャンネルミキサー/白黒の全変種)、
   `convolve`(任意カーネル = シャープ/エンボス/輪郭/方向ブラー)、`curves`、`lut`。
   この 3〜4 個で大半のフィルタは「JSON レシピのデータ違い」になり、追加にコンパイル不要となる
2. **既存エコシステムの取り込み口**: .cube LUT(数千の既存資産が直流入)、
   SVG/CSS フィルタ仕様互換(feColorMatrix / feConvolveMatrix — W3C 仕様は無料の検証値付きフィルタ定義集)
3. **プリセット = 名前付きレシピ**: 正規化ハッシュ付き JSON をそのまま配布資産化。
   `presets/` に用途別ルック(アイキャッチ標準、EC 商品、フィルム風等)を蓄積し、
   コミュニティ投稿もレシピ JSON の PR として受けられる。MCP ツール契約は太らない
4. **量産体制**: 各フィルタ = 小さな純関数 + ゴールデン + proptest のテンプレ化により、
   サブエージェント並列での安全な量産が可能。品質の錨は参照画像との数値照合(視覚回帰)

ライセンス注意: G'MIC(GPL)等コピーレフト由来の移植は取り込まない。W3C 仕様・論文アルゴリズム・
パブリックドメイン実装を参照源とする。

## Agent UX の規律(MCP ツール構成の洗練)

能力がいくら増えても AI エージェントが使いこなせなければ意義を没却する。以下を不変の規律とする:

1. **ツール = 作業動詞、能力 = レシピ語彙**: ツールは作業ループ
   (知覚 inspect/detect → 検証 preview/compare → 確定 apply → 届ける export)に対応する動詞のみ。
   op 追加でツールは増やさない。ツール追加が許されるのは「検出系」「検証系」「語彙参照系」のみ
2. **語彙の段階的開示**: op が増えたら `apply_transform` の inputSchema に全 op を埋め込まない
   (tools/list のトークン費が接続ごとに膨張するため)。
   - 常時: ツール説明にはループ + レシピの形 + 代表例1つだけ
   - オンデマンド: `list_operations`(軽量カタログ)+ `explain_operation`(完全スキーマ + 例)
   - エラーが教師: 構造化エラーに有効値の列挙・「もしかして」・recovery 手順を含め、1往復で自己修復可能にする
3. **プリセット = 語彙の圧縮**: 高頻度ルックはプリセット名1語で済ませ、精密制御時のみ生 DSL に降りる
   2層言語として設計する
4. **返却の連鎖性**: すべての変更系ツールは「次のステップに必要な値」(revision_id、寸法、警告、パス)を
   structuredContent で返し、再問い合わせなしで連鎖できることを保つ
5. **エージェント eval をリリースゲートに**: 実務タスク(横倒し写真→16:9 アイキャッチ等)を
   MCP 接続済みエージェントに解かせ、成功率・往復数・消費トークンを計測する。
   ツール説明・エラー文言・スキーマ変更はこの eval で回帰確認する(実運用 FB の P2 は eval が拾うべき欠陥だった)

## 横断的な規律(全フェーズ共通)

- **決定論の維持**: 新 op ごとにゴールデン + proptest(決定論・値域・冪等性が定義できる op は冪等性)を必須とする
- **レシピ互換性**: canonical hash を壊す変更は DSL バージョンフィールドで世代分離。既存 revision の再現性は永久保証
- **MCP ツール面は薄く保つ**: op が増えてもツールは増やさない(apply_transform / render_preview に乗せる)。ツール追加は「検出系」と「検証系」のみ
- **性能**: 大画像はタイル処理を Phase B で設計に織り込む。GPU(wgpu)は Phase D 以降の最適化として温存
- **参照実装との照合**: 色変換は ICC 公式テストセット、ブレンドは W3C 仕様値、で数値検証

## 優先順位の考え方

コンテンツメディア制作の実需(本プロジェクトの原点)から見ると、価値の 8 割は Phase A+C(全体調整 + 部分調整)で出る。Phase D は「Photoshop 完備」の看板に必要だが、実務投入は A→B→C の順で回収しながら進める。

## リリース計画への具体化(2026-08-21)

フェーズ A〜E を、リリース単位の作業パッケージに分解する。原則:
**1リリース = 1つの設計判断 + 数個の op 群**。破壊的変更は v0.4 の1回に集約する。

> **注**: 以下の `v0.X`(v0.2, v0.3, ...)は本セクション内の**計画上の作業パッケージ ID**であり、
> 実際にタグ付けされたリリースバージョンと 1 対 1 対応しない。実際の出荷記録は:
> 実タグ **v0.2.0** が本セクションの plan-v0.2 〜 plan-v0.8 の作業をまとめて含み、
> 実タグ **v0.3.0** が op/プリセットのコンテンツ拡張(§9.10 参照)にあたる。
> 実装として確定した内容の一次情報は常に `docs/DESIGN.md` §9 側を参照すること。

### v0.2 — 調整系の第一波 + 語彙参照ツール(Phase A 前半)

- op 追加: `perspective`(4点指定 or 縦/横キーストーン角。実運用 FB P4)、
  `color_matrix`(4×5 行列 = セピア/白黒/色相回転/チャンネルミキサーのメタ op)、
  `curves`(チャンネル別制御点、単調3次補間 → 256 LUT)、`levels`(curves の糖衣)、
  `blur`(gaussian σ)、`median`、`unsharp_mask`(amount/radius/threshold)
- ツール追加(語彙参照系、Agent UX 規律 #2): `list_operations` / `explain_operation`。
  **op 数が2桁に乗る前に必須**(inputSchema 肥大によるトークン費防止)
- ビルトインプリセット v0: `presets/` に名前付きレシピ(eyecatch_16_9 等)を同梱し、
  apply_transform が `preset` 名を受けられるようにする
- エージェント eval ハーネス v0: 実務タスク 10 本(実運用 FB 由来)+ headless 実行スクリプト
  + 成功率/往復数の記録。リリース前ゲートとして手動実行

### v0.3 — データ資産の取り込み口(Phase A 後半)

- op 追加: `lut`(.cube 1D/3D、四面体補間)、`white_balance`(色温度/ティント)、
  `hsl`(8色相域別の H/S/L シフト = Lightroom HSL パネル)、`convolve`(任意カーネル ≤9×9)
- **設計判断(このリリースの本丸)**: レシピからの他アセット参照。
  .cube ファイルを `import_asset` でストアに入れ、`{"op":"lut","lut_revision_id":"rev_..."}`
  と参照する。ハッシュには参照 revision id を含める(revision は不変なので決定論は保たれる)。
  この「レシピ → アセット参照」パターンは v0.5 のマスク参照の先行実装になる
- プリセットパック第1弾(フィルム風/EC商品/アイキャッチ各数種)を .cube + レシピで

### v0.4 — 画素エンジン v2(Phase B。唯一の破壊的リリース)

- 内部表現を f32 リニアライトへ。入口 sRGB EOTF → 作業空間、出口で逆変換。
  `ENGINE_VERSION = "atx-core/2"`、v1 ゴールデンは凍結アーカイブ
- **最大の技術リスク: f32 のクロスプラットフォーム決定論**。対策を先に規約化する:
  - トーン系は f64 で固定アルゴリズム計算した 65536 エントリ LUT 経由(libm 差を遮断)
  - 幾何補間は明示的丸め、SIMD 自動ベクトル化に依存する reassociation を禁止
  - CI の mac/Linux 両アームでゴールデン一致を必須ゲート化
  - **v0.2 期間中に小さな f32 パイプラインの spike を作り、両 OS 一致を先に実証する**
    (ここが崩れると Phase B 全体の工法を変える必要があるため、最優先の検証項目)
- 16bit I/O(PNG16)、`lcms2` feature flag(ICC 変換の実体化)

### v0.5 — マスクと局所適用(Phase C)

- マスク = グレースケール revision(v0.3 の参照パターンを再利用)
- 調整系 op 全てに `mask: {revision_id, invert?, feather_px?}` を追加
- 新ツール `generate_mask`(検出系/生成系): linear_gradient / radial_gradient /
  luminosity_range / color_range。決定論的
- `render_preview` に `overlay: "mask"`(マスク可視化)
- ML マスク(被写体/空)は **v0.5 に含めない**。onnxruntime + モデル配布の設計
  (サイズ・ライセンス・決定論)が別問題なので、需要を見て C2 として切り出す

### v0.6 — レイヤーグラフ前半(Phase D)

- レシピ DSL v2: `recipe_version: 2`、`layers: [{source, ops, mask, blend_mode, opacity}]`。
  v1 レシピは「1レイヤー」として無損失に読み込み(ハッシュは世代分離)
- ブレンドモード separable 系 12 種(W3C compositing 仕様値でゴールデン検証)

### v0.7 — レイヤーグラフ後半(Phase D 完)

- 非 separable 系(hue/saturation/color/luminosity)
- `clone` / `heal`(PatchMatch、シード・反復固定で決定論)
- `compare_revisions` に diff モード(差分ヒートマップ)

### v0.8+ — 入出力の翼(Phase E、需要駆動)

RAW(rawler)→ レンズ補正(lensfun DB)→ PSD 読み → resvg 焼き込み → LUT 書き出し。
順序は実利用の要望順で入れ替え可。

### v1.0 の定義

- 完備性3条件(§冒頭)を満たす
- eval スイート(その時点で 20+ タスク)成功率 ≥ 規定値
- 全 op にゴールデン + proptest、クロスプラットフォーム決定論 CI ゲート

### 横断リスクと先行検証

| リスク | 影響 | 先行検証 |
|---|---|---|
| f32 クロスプラットフォーム決定論 | Phase B 以降全部 | v0.2 中に spike(最優先) |
| レシピの他アセット参照設計 | LUT・マスク・レイヤー | v0.3 で小さく確立 |
| スキーマ肥大によるトークン費 | Agent UX | v0.2 の語彙参照ツールで先回り |
| op 量産時の品質劣化 | 全 op | op 仕様テンプレ(仕様→実装+ゴールデン+proptest)で工場化 |

### 体制運用

各リリースは今回と同じ工法で回す: 司令塔が設計判断と op 仕様書を確定 →
Opus/Sonnet に op 単位で並列委譲(仕様テンプレ準拠)→ 統合確認 → eval → タグ。
op 実装は互いに独立性が高く、1リリースあたりの並列度はさらに上げられる。

### v0.8 時点の RAW 判断(2026-08-21 調査、延期)

調査の結論: 技術的には実現可能(rawler 0.7.2 のデコードは整数演算で決定論的、
bilinear デモザイクは自前実装 S-M 規模、rawler の dng::writer で合成 DNG フィクスチャ生成可)
だが、以下により**需要発生まで延期**:

1. **ライセンス**: rawler は LGPL-2.1(imagepipe は LGPL-3.0、zenraw は AGPL で不採用)。
   本プロジェクトの MIT と厳密には非互換。採用するなら「raw feature flag で隔離 +
   方針の明文化」が必要 — **実装前に要・プロジェクト判断**
2. 需要未発生(Phase E は需要駆動)
3. v1 の正直なスコープは「リニアセンサー取り込み」であり、カメラ色行列変換なしでは
   実用 RAW 現像の品質に届かない(期待値管理が必要)

解禁時の手順: ライセンス判断の記録 → rawler dng::writer で合成 DNG PoC →
raw feature flag(rawler =0.7.2 固定ピン)→ 自前 bilinear デモザイク(決定論規約準拠)
→ decode_raw 経路 → 合成 DNG ゴールデン + CI 両アーム。
